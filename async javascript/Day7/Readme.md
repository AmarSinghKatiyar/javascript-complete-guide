# JavaScript Call Stack, Web APIs & Event Loop

Understanding the **Call Stack**, **JavaScript Engine**, **Browser Web APIs**, **Task Queues**, and the **Event Loop** is essential for understanding how JavaScript handles asynchronous operations.

---

## 1. Browser Environment

A browser provides several components that work together to execute JavaScript:

```text
Browser
│
├── JavaScript Engine
│   └── Call Stack
│
├── Web APIs
│   ├── Fetch API
│   ├── setTimeout()
│   ├── setInterval()
│   ├── DOM APIs
│   └── console.log()
│
├── Microtask Queue
│   └── Promises
│
├── Macrotask / Callback Task Queue
│   ├── setTimeout callbacks
│   ├── setInterval callbacks
│   └── other tasks
│
└── Event Loop
```

---

# 2. JavaScript Is Single-Threaded

JavaScript's main execution model is **single-threaded**.

This means that JavaScript code on the main thread executes **one piece of JavaScript at a time**.

For example:

```js
console.log("Start");

console.log("Hello");

console.log("End");
```

The code executes in order:

```text
Start
Hello
End
```

The **Call Stack** manages this synchronous execution.

---

# 3. JavaScript Engine

The JavaScript engine is responsible for executing JavaScript code.

Examples of JavaScript engines:

* Chrome → V8
* Firefox → SpiderMonkey
* Safari → JavaScriptCore

The engine contains the **Call Stack**, where JavaScript functions are executed.

---

# 4. Call Stack

The **Call Stack** keeps track of the functions currently being executed.

Example:

```js
function first() {
    second();
}

function second() {
    console.log("Hello");
}

first();
```

The Call Stack works approximately like this:

```text
first()
   ↓
second()
   ↓
console.log()
```

After a function finishes, it is removed from the stack.

```text
console.log() → removed
second()      → removed
first()       → removed
```

Eventually:

```text
Call Stack → Empty
```

---

# 5. Browser Web APIs

The browser provides APIs that are not part of the JavaScript language itself.

These are commonly called **Web APIs**.

Examples:

```text
setTimeout()
setInterval()
fetch()
DOM APIs
```

For example:

```js
setTimeout(() => {
    console.log("Timer finished");
}, 2000);
```

JavaScript does not sit inside the Call Stack waiting for 2 seconds.

Instead, the browser handles the timer using its Web APIs.

---

# 6. setTimeout()

Consider:

```js
console.log("Start");

setTimeout(() => {
    console.log("Timer");
}, 2000);

console.log("End");
```

The output is:

```text
Start
End
Timer
```

### What happens?

### Step 1

```js
console.log("Start");
```

It goes to the Call Stack and executes.

```text
Start
```

---

### Step 2

```js
setTimeout(...)
```

The timer is handled by the browser's Web API.

The JavaScript engine does **not** wait for the timer.

Conceptually:

```text
Call Stack
    │
    └── setTimeout()
             ↓
        Browser Web API
             ↓
        Timer starts
```

---

### Step 3

JavaScript continues executing:

```js
console.log("End");
```

So:

```text
Start
End
```

---

### Step 4

After the timer has finished, its callback becomes eligible to run and is placed into the **task queue** (often called the macrotask/callback task queue).

```text
Timer finishes
      ↓
Task Queue
      ↓
Event Loop
```

---

### Step 5

The Event Loop waits until the Call Stack is empty.

When the Call Stack is empty, the callback can be moved to the Call Stack.

```text
Task Queue
    ↓
Event Loop
    ↓
Call Stack
    ↓
console.log("Timer")
```

Output:

```text
Start
End
Timer
```

---

# 7. setTimeout(0)

A common misunderstanding is:

> `setTimeout(..., 0)` means the callback runs immediately.

It does **not** mean that.

Example:

```js
console.log("Start");

setTimeout(() => {
    console.log("Timer");
}, 0);

console.log("End");
```

Output:

```text
Start
End
Timer
```

Even with `0` milliseconds, the callback does not execute immediately.

It becomes eligible to run after the current synchronous JavaScript execution finishes.

So:

```text
Start
↓
End
↓
Timer
```

---

# 8. Task Queue / Macrotask Queue

Callbacks from many asynchronous browser operations are placed into a **task queue**.

This queue is also commonly called the:

* Task Queue
* Macrotask Queue
* Callback Queue

For example:

```js
setTimeout(() => {
    console.log("Timer");
}, 0);
```

The callback eventually becomes a task that can be processed by the event loop.

Other examples can include tasks generated by browser events.

---

# 9. Microtask Queue

JavaScript also has a **Microtask Queue**.

Promises use the microtask queue.

Example:

```js
console.log("Start");

Promise.resolve().then(() => {
    console.log("Promise");
});

console.log("End");
```

Output:

```text
Start
End
Promise
```

The Promise callback does not execute immediately.

It goes into the **Microtask Queue**.

```text
Promise
   ↓
Microtask Queue
```

---

# 10. Microtask Queue vs Macrotask Queue

The Microtask Queue has priority over the regular task/macrotask queue **after the current Call Stack becomes empty**.

Example:

```js
console.log("Start");

setTimeout(() => {
    console.log("setTimeout");
}, 0);

Promise.resolve().then(() => {
    console.log("Promise");
});

console.log("End");
```

Output:

```text
Start
End
Promise
setTimeout
```

Why?

### Synchronous code runs first

```text
Start
End
```

Then the Call Stack becomes empty.

The Event Loop processes the pending microtasks:

```text
Promise
```

Only after the microtask queue has been drained does it proceed to a task such as:

```text
setTimeout
```

Therefore:

```text
Start
End
Promise
setTimeout
```

---

# 11. Event Loop

The **Event Loop** coordinates the Call Stack and the queues.

A simplified model is:

```text
                 ┌─────────────────┐
                 │   Call Stack    │
                 └────────┬────────┘
                          │
                          │
                    Call Stack
                      becomes
                       empty
                          │
                          ▼
                 ┌─────────────────┐
                 │ Microtask Queue │
                 │   Promises      │
                 └────────┬────────┘
                          │
                   Process all
                    microtasks
                          │
                          ▼
                 ┌─────────────────┐
                 │  Task Queue /   │
                 │  Macrotask Queue│
                 └────────┬────────┘
                          │
                          ▼
                    Call Stack
```

The important simplified rule is:

> **Run synchronous code first. When the Call Stack is empty, drain the Microtask Queue. Then take an eligible task from the Task/Macrotask Queue.**

---

# 12. Complete Example

Consider:

```js
console.log("Start");

setTimeout(() => {
    console.log("setTimeout");
}, 0);

Promise.resolve().then(() => {
    console.log("Promise");
});

console.log("End");
```

### Step 1 — `console.log("Start")`

```text
Call Stack
    ↓
console.log("Start")
```

Output:

```text
Start
```

---

### Step 2 — `setTimeout()`

The timer is registered with the browser.

```text
setTimeout
    ↓
Browser Web API
    ↓
Timer
```

---

### Step 3 — Promise

The Promise callback is scheduled in the Microtask Queue.

```text
Microtask Queue
    ↓
Promise callback
```

---

### Step 4 — `console.log("End")`

It executes synchronously.

Output:

```text
End
```

---

### Step 5 — Call Stack becomes empty

Now the Event Loop can process pending asynchronous work.

First, it drains the Microtask Queue:

```text
Promise
```

---

### Step 6 — Task Queue

After the microtasks have been processed, the `setTimeout` callback can be taken from the task queue.

```text
setTimeout
```

Final output:

```text
Start
End
Promise
setTimeout
```

---

# 13. Important Rule

Remember this order:

```text
1. Synchronous JavaScript
          ↓
2. Call Stack becomes empty
          ↓
3. Microtask Queue
          ↓
4. Task / Macrotask Queue
```

In simple terms:

```text
Synchronous Code
       ↓
Call Stack
       ↓
Microtasks
(Promises)
       ↓
Tasks / Macrotasks
(setTimeout, etc.)
```

---

# 14. Important Correction

It is better to say:

> The browser provides Web APIs such as timers, Fetch, and DOM APIs.

Rather than saying:

> JavaScript sends every time-consuming statement to the Web API.

Not every slow operation is automatically moved to the Web API.

For example:

```js
while (true) {
    // Infinite synchronous loop
}
```

This remains on the Call Stack and blocks JavaScript execution.

The browser cannot simply move this JavaScript code to a Web API and continue.

---

# 15. Fetch API

The Fetch API is used for network requests.

Example:

```js
fetch("https://example.com")
    .then(() => {
        console.log("Data received");
    });
```

The network operation is handled by the browser/runtime.

When the Promise settles, the corresponding reaction is scheduled as a **microtask**.

So Promise callbacks associated with `fetch()` use the Microtask Queue.

---

# 16. setInterval()

`setInterval()` schedules a callback repeatedly.

Example:

```js
setInterval(() => {
    console.log("Hello");
}, 1000);
```

The browser manages the timer.

When the interval callback becomes eligible, it is scheduled as a task.

It does **not** interrupt currently running JavaScript.

If the Call Stack is busy, the callback has to wait.

---

# 17. DOM APIs

The browser also provides APIs for interacting with the DOM.

Example:

```js
const button = document.querySelector("button");

button.addEventListener("click", () => {
    console.log("Button clicked");
});
```

When the user clicks the button, the browser creates a task associated with the event handler.

The callback can execute when the JavaScript execution model allows it.

Think of JavaScript like this:

### Call Stack

> "What JavaScript code am I executing right now?"

### Web APIs

> "Browser, you handle this timer, network request, DOM event, etc."

### Microtask Queue

> "I have Promise callbacks waiting to run."

# 20. One-Line Summary

> **JavaScript executes synchronous code on the Call Stack. Browser Web APIs handle asynchronous browser operations. When their callbacks become eligible, they are scheduled into the appropriate queues. Once the Call Stack is empty, microtasks are drained before the event loop proceeds to the next task.**

# Call Stack

The **Call Stack** in JavaScript is a **LIFO (Last In, First Out)** data structure that keeps track of function execution.

It determines:

* Which function is currently executing
* Which function should execute next
* The order in which functions return
* Where execution should continue after a function finishes

### LIFO — Last In, First Out

For example:

```js
function first() {
    second();
}

function second() {
    third();
}

function third() {
    console.log("Hello");
}

first();
```

The Call Stack can be visualized as:

```text
first()
   ↓
second()
   ↓
third()
   ↓
console.log()
```

The last function added to the stack is the first one removed:

```text
console.log() → removed first
third()       → removed next
second()      → removed next
first()       → removed last
```

That's why the Call Stack follows the **LIFO (Last In, First Out)** principle.

### Simple Definition

> **The Call Stack is a LIFO data structure used by JavaScript to keep track of currently executing functions and their execution order.**


# Promise + setTimeout Execution Example

Consider the following code:

```js
console.log("hello start");

setTimeout(() => {
    console.log("i am a timer");
}, 0);

const promise = new Promise((resolve, reject) => {
    setTimeout(function () {
        resolve("Promise resolved");
    }, 0);
});

promise.then((data) => {
    console.log(data);
});

console.log("End");
```

The output is:

```text
hello start
End
i am a timer
Promise resolved
```

---

## Step-by-Step Execution

### 1. Synchronous Code Runs First

The first statement is:

```js
console.log("hello start");
```

It goes directly to the **Call Stack** and executes.

Output:

```text
hello start
```

---

### 2. First `setTimeout()`

Next:

```js
setTimeout(() => {
    console.log("i am a timer");
}, 0);
```

The timer is handled by the browser's **Web API**.

The callback does not execute immediately.

After the timer becomes eligible, its callback is placed into the **Task/Macrotask Queue**.

```text
setTimeout()
     ↓
Browser Web API
     ↓
Task/Macrotask Queue
```

---

### 3. Promise Constructor Runs Synchronously

Next:

```js
const promise = new Promise((resolve, reject) => {
    setTimeout(function () {
        resolve("Promise resolved");
    }, 0);
});
```

The **Promise constructor itself executes synchronously**.

However, the `setTimeout()` inside the Promise is asynchronous.

```text
Promise constructor
        ↓
    setTimeout()
        ↓
   Browser Web API
        ↓
   Task/Macrotask Queue
```

At this point, the Promise is still **pending**.

```text
Promise → Pending
```

---

### 4. `promise.then()`

Next:

```js
promise.then((data) => {
    console.log(data);
});
```

The `.then()` callback does **not** immediately go into the Microtask Queue.

Why?

Because the Promise is still pending.

The Promise will only be resolved later when this code executes:

```js
resolve("Promise resolved");
```

---

### 5. `console.log("End")`

Next:

```js
console.log("End");
```

This is synchronous code, so it executes immediately.

Output:

```text
hello start
End
```

At this point, the **Call Stack becomes empty**.

---

# What Happens Next?

There are now two timer callbacks waiting to execute.

Conceptually:

```text
Task / Macrotask Queue

┌─────────────────────────────┐
│ 1. First timer callback     │
│ 2. Promise resolve timer    │
└─────────────────────────────┘
```

---

## 6. First Timer Executes

The first timer callback runs:

```js
console.log("i am a timer");
```

Output:

```text
i am a timer
```

So far:

```text
hello start
End
i am a timer
```

---

## 7. Second Timer Executes

Now the second timer callback runs:

```js
resolve("Promise resolved");
```

This changes the Promise from:

```text
Pending
```

to:

```text
Fulfilled
```

```text
resolve()
   ↓
Promise fulfilled
```

---

## 8. `.then()` Callback Goes to Microtask Queue

Because the Promise is now fulfilled, its `.then()` callback becomes a **microtask**.

```js
promise.then((data) => {
    console.log(data);
});
```

The callback goes into:

```text
Microtask Queue
```

Conceptually:

```text
resolve()
   ↓
Promise fulfilled
   ↓
Microtask Queue
   ↓
promise.then()
```

---

## 9. Microtask Executes

The Event Loop processes the microtask:

```js
console.log(data);
```

Output:

```text
Promise resolved
```

Therefore, the final output is:

```text
hello start
End
i am a timer
Promise resolved
```

# Important Concept

A very important point is:

> **Microtasks have priority over tasks only when they are actually present in the Microtask Queue.**

In this example, the Promise's `.then()` callback cannot enter the Microtask Queue until the second `setTimeout()` calls:

```js
resolve("Promise resolved");
```

Therefore, the first timer can execute before the Promise callback.

# Compare With an Already Resolved Promise

Consider this different example:

```js
console.log("Start");

setTimeout(() => {
    console.log("Timer");
}, 0);

Promise.resolve().then(() => {
    console.log("Promise");
});

console.log("End");
```

Output:

```text
Start
End
Promise
Timer
```

Why?

Because this Promise is **already resolved**:

```js
Promise.resolve()
```

Therefore, the `.then()` callback can immediately be scheduled as a microtask.

The order becomes:

```text
Synchronous Code
       ↓
Call Stack Empty
       ↓
Microtask Queue
       ↓
Promise
       ↓
Task Queue
       ↓
Timer
```

---

# Key Difference

### Your Example

```js
setTimeout(() => {
    resolve("Promise resolved");
}, 0);
```

The Promise is resolved **inside a timer**.

Therefore:

```text
Timer
  ↓
resolve()
  ↓
Microtask
```

So the output is:

```text
i am a timer
Promise resolved
```

### Already Resolved Promise

```js
Promise.resolve().then(...)
```

The Promise is already resolved.

Therefore:

```text
Microtask
  ↓
Promise callback
```

And it can run before a timer task.

---

# Final Rule to Remember

```text
Synchronous Code
       ↓
Call Stack becomes empty
       ↓
Process Microtasks
       ↓
Process next Task/Macrotask
       ↓
Process Microtasks again
       ↓
Next Task/Macrotask
       ↓
...
```

The most important idea is:

> **A Promise callback does not automatically run before every `setTimeout()`. First, the Promise must become fulfilled/rejected and its reaction must be placed into the Microtask Queue.**



# Starvation 
# ============================================================================================================================================
# Microtask Starvation

Microtask starvation happens when microtasks continuously create more microtasks, preventing the event loop from moving on to the next task/macrotask.

## 100 Microtasks Are Not Necessarily Starvation

Suppose the microtask queue contains 100 Promise callbacks:

```javascript
for (let i = 0; i < 100; i++) {
    Promise.resolve().then(() => {
        console.log("Microtask");
    });
}

setTimeout(() => {
    console.log("Timer");
}, 0);
```

This is **not necessarily starvation**.

The event loop can process:

```text
Current JavaScript
       ↓
100 Microtasks
       ↓
Microtask queue becomes empty
       ↓
Timer task
```

Eventually, the microtask queue becomes empty, so the event loop can continue to the timer.

The important point is:

> **A large microtask queue is not automatically starvation.**

---

# Infinite Microtask Chain

Starvation occurs when processing a microtask continuously adds another microtask.

Example:

```javascript
function createMicrotask() {
    Promise.resolve().then(() => {
        console.log("Microtask");

        createMicrotask();
    });
}

createMicrotask();

setTimeout(() => {
    console.log("Timer");
}, 0);
```

The important part is:

```text
Microtask 1
    ↓
creates Microtask 2
    ↓
Microtask 2
    ↓
creates Microtask 3
    ↓
Microtask 3
    ↓
creates Microtask 4
    ↓
...
```

The microtask queue never becomes empty.

Therefore, the timer may never get a chance to execute.

```text
┌─────────────────────────────┐
│        Microtask Queue      │
│                             │
│  Microtask                  │
│      ↓                      │
│  creates another            │
│      ↓                      │
│  Microtask                  │
│      ↓                      │
│  creates another            │
│      ↓                      │
│  Microtask                  │
│      ↓                      │
│     ...                     │
└─────────────────────────────┘
              ↓
       Never reaches
              ↓
       Timer / next task
```

This is **microtask starvation**.

---

# Why Does This Cause Starvation?

The event loop generally processes the current task and then performs a microtask checkpoint.

During that checkpoint, newly queued microtasks are also processed.

For example:

```javascript
Promise.resolve().then(() => {
    console.log("A");

    Promise.resolve().then(() => {
        console.log("B");
    });
});
```

The second Promise callback is added while microtasks are already being processed.

Conceptually:

```text
Microtask A
    ↓
creates Microtask B
    ↓
Microtask B
```

The event loop does not simply say:

> "I processed the original microtask, so now I must immediately run the timer."

It continues processing the microtask queue.

If every microtask keeps adding another microtask, the queue can remain non-empty indefinitely.

---

# Finite vs Infinite Microtask Creation

## Case 1 — Finite

```javascript
function createTasks(count) {
    if (count === 0) return;

    Promise.resolve().then(() => {
        console.log(count);
        createTasks(count - 1);
    });
}

createTasks(100);

setTimeout(() => {
    console.log("Timer");
}, 0);
```

The chain eventually ends:

```text
Microtask
   ↓
Microtask
   ↓
Microtask
   ↓
...
   ↓
100th Microtask
   ↓
Queue empty
   ↓
Timer executes
```

This can delay the timer, but it is not an infinite starvation situation.

---

## Case 2 — Infinite

```javascript
function forever() {
    Promise.resolve().then(() => {
        forever();
    });
}

forever();

setTimeout(() => {
    console.log("Timer");
}, 0);
```

Conceptually:

```text
Microtask
   ↓
new Microtask
   ↓
new Microtask
   ↓
new Microtask
   ↓
new Microtask
   ↓
...
```

The microtask queue keeps receiving more work.

The event loop therefore cannot reach the timer task.

This is **microtask starvation**.

---

# Important Interview Point

Do not say:

> "100 microtasks cause starvation."

Instead say:

> **A large number of microtasks can delay other tasks, but starvation occurs when microtasks continuously schedule more microtasks so that the microtask queue never becomes empty and the event loop cannot proceed to another task.**

The key difference is:

```text
Many finite microtasks
        ↓
Queue eventually empty
        ↓
Next task can execute
```

versus:

```text
Microtask
    ↓
creates microtask
    ↓
creates microtask
    ↓
creates microtask
    ↓
...
    ↓
Queue never becomes empty
    ↓
Other tasks are starved
```

---

# Microtask Starvation vs Normal Delay

These terms should also be distinguished.

### Normal delay

```text
1000 microtasks
       ↓
all finish
       ↓
timer executes
```

The timer was **delayed**, but it eventually executed.

### Starvation

```text
Microtask
   ↓
Microtask
   ↓
Microtask
   ↓
Microtask
   ↓
...
```

The next task is prevented from executing because the microtask work continues indefinitely.

---

# Another Example Using queueMicrotask()

Starvation is not limited to Promises.

`queueMicrotask()` also adds work to the microtask queue.

```javascript
function loop() {
    queueMicrotask(() => {
        console.log("microtask");
        loop();
    });
}

loop();

setTimeout(() => {
    console.log("Timer");
}, 0);
```

Conceptually:

```text
queueMicrotask()
       ↓
Microtask executes
       ↓
queueMicrotask()
       ↓
Microtask executes
       ↓
queueMicrotask()
       ↓
...
```

Again, the microtask queue keeps being replenished.

---

# Key Rule

Remember this simple rule:

```text
Many microtasks ≠ starvation

Continuously generated microtasks
+
microtask queue never becoming empty
+
other tasks unable to get their turn
=
```
